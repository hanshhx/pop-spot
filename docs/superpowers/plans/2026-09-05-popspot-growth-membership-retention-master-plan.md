## 1. 목표와 범위

### 1.1 목표

서비스의 방향은 **“팝업 정보를 찾는 사이트”에서 “내 취향과 방문 계획을 기억하고, 놓치기 전에 알려주는 서비스”로 확장하는 것**임.

| 목표 | 원하는 변화 | 잘못된 대체 지표 |
|---|---|---|
| 신규 유입 | 검색·공유로 실제 방문자가 들어옴 | 탭 클릭·페이지 조회만 늘어남 |
| 회원 전환 | 이용 가치를 느낀 사람이 계정을 만들고 하던 일을 이어 감 | 가입 안내를 많이 띄움 |
| 회원 활성화 | 저장·비교·계획·관심 설정을 실제로 이용함 | 누적 회원 수만 증가함 |
| 의미 있는 체류 | 후보를 탐색·비교하고 선택을 남김 | 정보 찾기가 어려워 오래 머묾 |
| 재방문 | 저장한 것과 관심 소식을 확인하려고 다시 옴 | 알림을 많이 보냄 |

- 일일 방문자 약 200명과 누적 회원 57명은 사용자가 제시한 서로 다른 기준의 수치임. 두 숫자를 나누어 가입 전환율로 사용하지 않음.
- 1차 트래픽 목표는 300명/일임. 동일 집계·시간대의 완료된 일별 방문자 수를 사용하고, 서로 겹치지 않는 두 7일 구간에서 각각 일평균 300명 이상인지 확인함.
- 최종 방향인 1,000명/일은 후속 확장 목표임. 기능별 예상 증가 인원을 근거 없이 배분하거나 달성 날짜를 약속하지 않음.
- 이 계획은 최근 방문 감소의 원인이 콘텐츠 부족이라고 판정하지 않음. 검색 유입 하락 진단과 콘텐츠·회원 개선은 별도 증거로 판단함.

1. 상세·랜딩·지도·전체 일정·공개 가이드는 로그인 없이 열 수 있어야 함.
2. 비회원의 현재 기기 저장·비교·저장 목록 확인을 7일 체험 만료로 막지 않는 방향임. 비용이 발생하는 AI 요청 제한은 별도 정책으로 다룸.

4. 자동 수집 시각과 사람이 공식 내용을 확인한 시각을 구분함. AI 확신도는 사실 검증의 대체물이 아님.
5. 미확인 정보를 무료·예약 불필요·영업 중으로 바꾸지 않음.
6. 출처 표시는 사진·카드뉴스·본문의 사용 허락을 대신하지 않음. 허용된 자료만 사용하고, 직접 방문한 경험과 공식 자료 정리를 구분함.
7. 미확인 체험·후기·대기시간·품절·연령 적합성을 생성하지 않음.
8. 정보는 한 번 관리하고 여러 화면이 재사용함. 사용자 확인 없이 기본 관심사를 몰래 확정하지 않음.
9. 저장·관심·계획은 비공개가 기본임. 공유는 사용자가 선택한 공개 콘텐츠를 대상으로 하고 개인 계정 정보는 포함하지 않음.

11. 정책 준수·검색 순위·광고 승인을 보장하는 문구를 쓰지 않음.
12. 이 문서 작성은 서비스 코드 변경·데이터 삭제·알림 발송·커밋·배포 승인과 구분함.

| 이메일 가입에 전화번호가 필수이며 가입 후 로그인으로 이동함 | 가입 과정이 길고 하던 일이 끊길 수 있음 | 단계별 실패를 측정하고 복구 수단과 함께 단순화함 |
| 웹 인증이 탭 세션 저장소 기반임 | 다음 방문의 로그인 유지가 보장되지 않음 | 일반 회원용 지속 세션을 보안 설계와 함께 검토함 |
| 종료 알림 코드가 있으나 기본 설정은 비활성임 | 코드 존재와 실제 사용 가능한 혜택이 다름 | 운영 설정·수신 선택·실제 전달을 별도 검증함 |
| 지도·근처 팝업·일정·가이드용 목록 재료가 이미 있음 | 비슷한 섹션을 더 만들어도 가치가 겹침 | 입장 조건·비교·선정 이유를 보완함 |

이 표만으로 회원 수가 적거나 방문자가 감소한 원인을 확정하지 않음. 특히 찜 이전 문제는 즉시 데이터 삭제가 확인되었다는 뜻이 아님.

## 4. 화면별 역할과 요구사항

| 화면 | 답할 질문 | 주요 행동 |
|---|---|---|
| 발견 | 아직 정하지 못했는데 무엇이 내 관심에 맞는가? | 가이드 읽기, 취향 선택, 관심 저장 |
| 상세 | 무엇을 할 수 있고, 어떤 조건으로 방문하는가? | 내용 확인, 저장, 비교에 추가, 공식 안내 확인 |
| 랜딩 | 이 지역·기간의 후보 중 무엇이 다른가? | 후보 비교, 관련 상세·가이드 이동 |
| 마이팝 | 내가 선택한 것을 어떻게 이어서 이용하는가? | 저장·계획 확인, 관심 소식 확인, 알림 설정 |

### 4.1 상세페이지 — 방문 결정을 위한 정보

**문제:** 소개 문장이 일반적이거나 안내 이미지에 핵심 정보가 묻혀 있으면 방문자가 다시 검색해야 함.

**바꿀 내용:**

- ‘여기서 할 수 있는 것’을 확인된 사실 2~4개로 정리함. 체험 내용, 전시·촬영 조건, 상품 종류·구매 제한, 참여 행사 조건을 다룸.
- ‘방문 전 30초 확인’에 운영시간·마지막 입장, 입장료와 별도 체험 비용, 예약 방식·공식 링크, 제한사항을 표시함.
- 공식 출처·확인일·미확인 항목을 표시함. 기존 출처 영역을 보완하며 같은 영역을 중복 추가하지 않음.
- 근처 팝업은 위치뿐 아니라 운영 기간의 겹침을 설명함. 확인된 휴무·운영시간이 없으면 실제 방문 가능성을 보장하지 않음.
- 저장·비교·공식 예약·길찾기를 자연스럽게 연결함. 체류시간을 늘리려고 외부 이동 버튼을 숨기지 않음.

**사용자에게 달라지는 점:** 체험과 입장 조건을 빠르게 확인하고, 후보를 저장·비교할 수 있음.

**선정 기준:** 공식 자료가 있고 정보 확인이 가능하며, 현재 또는 가까운 미래의 방문 수요가 있는 팝업을 우선함. 유입 순위만으로 곧 종료될 행사에 작업을 몰지 않음.

### 4.2 랜딩페이지 — 목록에서 비교로

**문제:** 팝업이 나열되어 있어도 서로 다른 점을 알기 위해 상세를 반복해서 열어야 함.

**바꿀 내용:**

- 선택한 3개 랜딩에서 5~8개 후보의 주요 경험·입장 방식·비용·종료일을 비교함. 확인된 후보가 적으면 실제 수만 보여줌.
- 모바일에서는 가로로 긴 표 대신 짧은 비교 카드로 읽을 수 있게 함.
- 기존 ‘지금 고른다면’에 확인된 선택 이유를 붙임. 현장 입장 가능, 확인된 체험, 판매 품목, 운영 기간 겹침 등을 사용함.
- FAQ는 랜딩마다 실제 답할 수 있는 방문 질문 2~3개로 보완함. 지역·주간·월간·브랜드 페이지의 질문을 구분함.
- 상세와 동일한 정보를 재사용하고, 일반적인 안내 문구만 반복하여 페이지를 늘리지 않음.

**사용자에게 달라지는 점:** 여러 후보의 차이를 한 화면에서 이해하고 원하는 조건으로 좁힐 수 있음.

### 4.3 최대 3곳 비교 — 의미 있는 참여

**문제:** 저장은 가능해도 후보를 나란히 놓고 선택하는 행동으로 이어지기 어려움.

**바꿀 내용:**

- 상세·랜딩·마이팝에서 최대 3개의 후보를 비교 목록에 넣고 뺄 수 있게 함.
- 비교 항목은 주요 경험·입장 조건·운영 기간·비용·위치로 제한함.
- 1개만 고르면 두 번째 후보를 선택할 수 있도록 안내함. 비교 항목이 없으면 임의 정보를 채우지 않음.
- 현재 기기의 비교는 비회원에게도 제공함. 계정 저장을 선택하면 로그인 후 그 비교 상태로 복귀함.
- 첫 버전에서는 최적 경로 계산기나 공동 편집 기능을 추가하지 않음.

**사용자에게 달라지는 점:** 어떤 곳을 방문할지 결정하는 과정을 사이트 안에서 끝낼 수 있음.

### 4.4 스탬프 → 발견

**문제:** 방문 기록을 쌓아야 의미가 생기는 스탬프는 첫 방문자에게 가치가 제한적임. 가이드만 넣으면 읽는 행동에서 끝날 수 있음.

**최종 명칭:** 탭은 ‘발견’임. ‘가이드’는 발견 안의 콘텐츠 유형임. 별도의 가이드 탭을 추가하지 않음.

**바꿀 내용:**

1. 공개 가이드 3개를 제공함. 주제는 함께 방문할 곳, 확인된 방문 조건, 전시·체험·굿즈 목적별 비교임.
2. 가이드마다 대상 독자·선정 이유·팝업 2~4곳의 차이·주의사항·적용 기간·확인일·관련 링크를 넣음.
3. 지역과 관심 분야를 선택하면 조건에 해당하는 실제 팝업을 보여줌. 처음에는 최대 6개 카드와 ‘관심 있어요 / 넘기기’만 제공함.
4. ‘관심 있어요’는 기존 찜에 연결함. 별도의 중복 저장함을 만들지 않음. ‘넘기기’는 이번 탐색에서 제외하는 뜻이며 영구 취향으로 단정하지 않음.
5. 추천 이유는 사용자가 고른 조건으로 설명함. 근거 없는 일치율·인기도·개인 성향 점수는 사용하지 않음.
6. 결과는 로그인 없이 보여줌. 4단계에서는 현재 기기의 관심 설정으로 탐색하게 하며, 계정 보관·동기화는 5단계 검증 뒤 제공함. 그때부터 계정에 관심 설정을 보관하려는 사용자를 선택적으로 로그인하게 함.
7. 홈에 대표 가이드를, 관련 상세·랜딩에 해당 안내 링크를 배치함. 모바일 더보기의 이름만 바꾸고 끝내지 않음.

**공개 주소 원칙:** 기존 랜딩과 질문·내용이 같으면 해당 랜딩을 보강하여 연결함. 질문과 답이 충분히 다른 가이드만 독립 공개 주소를 가짐. 사용자별 취향 결과 주소를 대량 색인하지 않음.

**공유 원칙:** 로그인·앱 설치 없이 열리며 미리보기에 실제 제목과 적용 기간이 표시되어야 함. 공개 가이드 공유는 기존 공유 기능을 재사용함. 개인 취향·저장 목록은 자동 공개하지 않음.

**스탬프 정리:** 웹·앱 진입점, 상세의 인증 버튼, 마이페이지 등급·카운트, 소개 문구를 함께 점검함. 신규 적립 종료와 기존 기록 삭제는 별도 결정임. 첫 변경에서 기존 기록·테이블은 삭제하지 않으며, 구버전 앱 호출과 기존 링크의 안내 경로를 확인함.

**사용자에게 달라지는 점:** 기록이 없는 첫 방문자도 즉시 탐색하고 선택을 남기며 친구에게 안내를 보낼 수 있음.

### 4.5 마이페이지 → 마이팝

**문제:** 계정·실적 중심 화면은 다음 방문에 필요한 정보를 먼저 제공하지 못함.

**최종 구성 순서:**

1. 이번에 갈 곳: 저장한 진행 중 팝업·마감 가까운 팝업·직접 지정한 방문 계획임.
2. 관심 있는 새 팝업: 선택한 지역·분야의 새로 등록된 행사임. 새 정보가 없으면 빈 알림 배지나 가짜 업데이트를 만들지 않음.
3. 저장한 팝업과 계획: 예정·진행 중·종료를 구분하고 기존 찜·코스·캘린더를 연결함.
4. 관심·알림 설정임.
5. 계정 설정: 프로필·로그아웃·탈퇴 등을 찾기 쉽게 제공함.

- 회원 가입 직후에는 방금 저장한 내용을 최우선으로 보여줌.
- 비회원에게는 현재 기기의 보관 내용을 보여주고 기기 간 동기화의 차이를 설명함.
- ‘저장한 곳’과 ‘방문하기로 확정한 곳’을 동일하게 취급하지 않음. 방문일은 사용자가 정한 경우에만 표시함.
- ‘새로 등록됨’, ‘오늘 개장함’, ‘정보가 변경됨’을 구분함. 마지막 표현은 실제 변경 이력이 있을 때만 사용함.
- 종료된 저장 기록을 곧바로 지우지 않으며 현재 방문 추천과 보관 기록을 분리함.
- 관심 목록은 발견의 전체 추천 목록을 반복하는 것이 아니라, 사용자가 계정에 저장한 조건에 해당하는 새 정보를 보여주는 역할임.

**사용자에게 달라지는 점:** 계정 상태를 보러 오는 것이 아니라, 저장한 선택과 다음 방문 계획을 이어 쓰러 오게 됨.

## 5. 비회원·회원 경계와 가입 흐름

| 현재 기기에서 비회원 이용 | 계정에 제공할 추가 가치 |
|---|---|
| 공개 콘텐츠·지도·전체 일정 열람 | 여러 기기에서 저장 목록 동기화 |
| 찜·저장 목록·최대 3곳 비교 | 관심 설정·계획 보관과 복원 |
| 취향 선택·결과 확인 | 요청한 개인 알림의 관리 |
| 공개 가이드 공유와 열람 | 개인 데이터의 변경·삭제 관리 |

### 5.1 안내 시점

- 저장 직후에는 먼저 저장 결과를 알려 줌. 저장 성공이 확인되지 않으면 ‘저장됨’이라고 말하지 않음.
- 계정 보관 안내는 첫 가치 행동 뒤 비차단형으로 제공함. 닫은 안내를 같은 방문에서 반복 강요하지 않음.
- 취향 결과를 확인한 뒤 계정에 설정을 보관할 수 있음을 설명함.
- 종료 알림을 직접 요청한 경우 수신 계정과 설정을 확인함.
- ‘가입하면 볼 수 있음’보다 ‘하던 것을 다른 기기에서도 이어 볼 수 있음’을 설명함.

### 5.2 반드시 이어져야 하는 흐름

- 비회원 저장 → 로그인 또는 가입 → 서버의 기존 저장과 합침 → 원래 화면·비교 상태 복귀임.
- 이메일·소셜·추가 인증이 필요한 경로에서 동일한 완료 처리를 사용함.
- 로그인 취소·오류에도 비회원 저장과 비교 상태를 보존함.
- 이전 실패 항목은 남겨 재시도하고, 성공한 항목만 계정 보관 완료로 표시함.
- 반복·동시 이전에도 중복이나 저장 해제가 발생하지 않는 ‘저장 상태 설정’ 방식으로 설계함. 기존 토글 호출을 재사용해도 안전하다고 가정하지 않음.
- 복귀 주소는 허용된 내부 화면만 받음. 다른 계정으로 재로그인할 때 개인 정보가 섞이지 않도록 소유권을 서버에서 검증함.

### 5.3 가입 단순화와 로그인 유지

- 이메일 가입 단계별 이탈·실패를 측정함. 소셜 로그인의 실제 성공률도 별도로 봄.
- 전화번호 필수 여부는 계정 찾기와 복구 수단을 함께 검토한 뒤 결정함. 입력란만 지워 기존 복구를 깨뜨리지 않음.
- 이메일 가입 직후 다시 처음부터 로그인해야 하는 흐름을 개선하되, 인증·약관 확인을 생략하지 않음.
- 일반 회원의 지속 로그인은 안전한 세션 설계와 함께 별도 개발 단위로 처리함. 단순한 장기 토큰 저장으로 해결하지 않음.
- 세션 만료·폐기·로그아웃·계정 전환·요청 위조 방어와 관리자 재인증을 검증함.
- 로그인 유지가 배포·검증되기 전에는 이를 가입 혜택으로 표시하지 않음.

- [ ] 저장·마감·기존 계획을 상단으로 이동함. 계정 설정·스탬프 실적과 분리함.
- [ ] 저장 0개, 진행 중 0개, 종료 항목만 존재, 데이터 오류 상태를 각각 설계함.
- [ ] 비회원 현재 기기 보관과 회원 계정 보관의 표시를 구분함.
- [ ] 작은 화면에서 목록·삭제·상세 이동·로그아웃·계정 설정을 확인함.
- [ ] 관심 소식이 아직 구현되지 않았다면 해당 혜택을 가짜 카드로 보여주지 않음.

### 7.4 작업 3 — 콘텐츠와 비교

- [ ] 공식 자료 확인 가능성과 남은 운영 기간을 기준으로 상세 10개와 연관 랜딩 3개를 선정함.
- [ ] 항목별 근거와 확인 여부를 정리하고 동일 데이터를 재사용함.
- [ ] 최대 3곳 비교의 추가·제거·이동·미확인 상태를 구현 계획으로 구체화함.
- [ ] 기간 미상·같은 날짜 시작/종료·휴무 미상·중복 행사·종료 후 방문을 테스트함.
- [ ] 잘못된 무료·예약 불필요·도보 시간·추천 점수가 표시되지 않음을 검수함.

### 7.5 작업 4 — 발견과 스탬프 종료

- [ ] 기존 랜딩으로 답할 수 있는 가이드는 그 주소를 재사용함.
- [ ] 가이드 3개의 공개 열람·공유 미리보기·실제 링크 도착을 확인함.
- [ ] 지역·분야 선택, 최대 6개 탐색 카드, 기존 찜 연결, 건너뛰기를 검증함.
- [ ] 현재 기기의 관심 선택만 지원하는 단계에서는 관심 설정의 계정 동기화를 가입 혜택으로 안내하지 않음.
- [ ] 선택 조건의 재고가 없으면 조건 완화 안내를 제공하고 임의의 추천을 만들지 않음.
- [ ] 웹·앱·기존 링크·구버전 앱의 스탬프 진입을 목록화하고 종료 안내를 마련함.
- [ ] 기존 스탬프 기록을 보존하며 홈·상세·랜딩에서 발견으로 연결함.

### 7.6 작업 5 — 재방문

- [ ] 계정에 저장한 관심 조건이 다른 기기에서 같은 의미로 복원됨을 확인함.
- [ ] 새 등록과 개장·수정의 표시가 서로 섞이지 않음을 확인함.
- [ ] 선택한 사용자에 한해 종료 알림을 시험 발송하고 수신·링크 이동을 확인함.
- [ ] 재실행·종료일 수정·수신 취소·탈퇴·메일 실패의 동작을 검증함.
- [ ] 발송량이 아니라 알림을 통한 실제 도착과 이후 행동을 관찰함.

#### 운영 설정 활성화는 개발 선행조건이 아니라 최종 출시 관문임

`WishlistExpiryScheduler` 는 `popspot.wishlist.enabled` 가 **기본 `false`** 이고 매일 09:00 KST 에 도는 구조임. 이 값을 먼저 켜면 **중복 방지와 수신 동의가 검증되지 않은 코드를 실제 사용자에게 실행**하게 됨. 아래가 모두 끝난 뒤에만 켬.

- [ ] 명시적인 알림 신청과 취소
- [ ] 알림 대상 계산 테스트
- [ ] 중복 발송 방지
- [ ] 이미 종료되거나 정보가 바뀐 팝업 제외
- [ ] 테스트 계정에만 보내는 시험 모드
- [ ] 발송 실패와 재시도 정책
- [ ] 개인정보 처리방침과 수신 내역
- [ ] 알림 링크의 실제 이동 확인

**`~/popspot.env` 에 값을 넣는 것만으로 충분하다고 단정하지 않음.** 실행 중인 서비스가 그 파일을 실제로 읽었는지, 재시작 후 적용됐는지를 확인함(배포 확인 방식은 `swap-jar.sh` 와 같은 근거를 씀).

**완료 증거**는 "설정 파일에 true 가 있음" 이 아니라 다음임:

> 재시작된 운영 프로세스가 활성 설정을 읽었고, 허용한 테스트 계정에 정확히 한 번 전달됐으며, 취소 후에는 더 이상 전달되지 않음.

## 8. 성공 지표와 판정 규칙

### 8.1 정의

| 지표 | 분자·분모 또는 측정 방식 | 주의점 |
|---|---|---|
| 방문자 | 동일 도구·집계·시간대의 완료된 일별 방문자 | 일별 방문 합은 기간 전체의 중복 제거 방문자와 다름 |
| 가입 과정 완료율 | 같은 관찰 집단에서 가입 완료한 수 / 가입 시작한 수 | 기존 회원 로그인과 신규 가입을 구분함 |
| 제안 후 가입 | 가입 제안에 노출된 비회원 중 가입 완료한 수 | 제안을 안 본 전체 방문자와 혼합하지 않음 |
| 회원 활성화 | 가입 후 7일 안에 저장·계획·관심 설정 중 하나를 완료한 신규 회원 / 7일 관찰이 완료된 신규 회원 | 가입 전 찜의 성공적 이전은 따로 표시함 |
| 회원 재방문 | 가입 후 1~7일, 1~28일 안에 다시 핵심 행동을 한 회원 비율을 각각 측정함 | 각 창의 관찰이 끝난 집단만 포함함. 정확히 7일째 재방문과 혼동하지 않음 |
| 비교·저장 참여 | 기능을 실제 이용한 방문 수와 해당 기능 노출 방문 수 | 버튼 클릭·화면만 열림·저장 실패를 완료로 세지 않음 |
| 공유 유입 | 공유 경로로 실제 도착한 방문과 이후 행동 | 복사·공유창 열기를 수신자 방문으로 세지 않음. 미리보기 봇·자기 확인은 가능한 범위에서 구분함 |
| 참여 시간 | 화면에 포커스가 있는 동안의 참여 시간 | 켜 둔 시간과 구분하고 시간 하나만 최적화하지 않음 |

- 로그인·회원 여부는 프로필 캐시 존재가 아니라 유효 인증을 기준으로 판단함.
- 익명 방문·계정·앱과 웹의 중복 제거에는 한계가 있으므로 측정 범위를 표시함. 동의나 정책 검토 없이 식별 범위를 확장하지 않음.
- 회원 수 57명이라는 누적 합계를 가입 성공률이나 잔존율의 분모로 그대로 사용하지 않음.
- 운영자·테스트·장애·부분 집계 구간을 표시함. 지표에서 무엇을 제외했는지 함께 기록함.

### 8.2 판정

1. 소수의 실제 사용자가 저장 → 로그인 → 다음 날 다시 찾기를 수행하는 과정부터 확인함. 인터뷰·사용성 확인은 정량적 전환율 증명의 대체물이 아님.
2. 첫 관찰에서는 사용·실패·복귀 단절을 우선 확인함. 검색 효과는 색인·관찰 기간과 표본이 충분해진 뒤 따로 평가함.
3. 기능을 많이 누르지만 저장·계획·다음 방문으로 이어지지 않으면 기능 수를 더 늘리기보다 막힌 단계를 수정함.
4. 가입 증가와 공개 콘텐츠 방문 감소가 동시에 발생하면 안내 시점·빈도·접근 제한을 점검함.
5. 비교·저장·예약 이동이 개선되면 참여 시간이 줄어도 실패로 판단하지 않음.
6. 알림 클릭이 적다는 이유로 발송 횟수를 자동으로 늘리지 않음.
7. 여러 변경을 동시에 배포했다면 개선을 특정 기능 하나의 효과로 단정하지 않음. 배포 시각과 영향을 받은 페이지·집단을 기록함.
8. 목표 개선률·회원 수·체류시간은 깨끗한 기준선을 확보한 뒤 정함. 업계 평균이나 임의의 퍼센트를 현재 프로젝트의 확정 목표로 사용하지 않음.

## 9. 출시·보안·되돌리기

- 인증 실패 증가, 계정 간 데이터 혼입, 저장 유실, 잘못된 수신자 발송은 해당 신규 기능의 즉시 중단·조사 사유임.
- 근거 없는 무료·예약 가능·운영 중 안내가 확인되면 해당 정보와 연결 추천을 우선 숨기고 확인함.
- 사용량이 적거나 지표가 출렁이는 것만으로 자동 원복하지 않음. 표본과 집계 상태를 먼저 확인함.
- 되돌리기는 새 진입·추천·발송 기능을 끄는 방식부터 준비함. 이미 저장된 기록을 지우거나 인증 취약점을 복원하는 방식으로 원복하지 않음.
- 관심·찜·계획의 읽기와 쓰기는 서버에서 계정 소유권을 검사함. 화면에서 숨기는 것으로 보호를 대신하지 않음.
- 웹에서 작은 범위를 먼저 검증하고 앱은 같은 데이터·계정 의미로 연결함. 초기 단계에서도 기존 앱 호환성 검사는 생략하지 않음.
- 계정 복구·보안 설정·발송 설정 변경은 관련 검증과 별도 승인 없이 편의 개선에 묶어 배포하지 않음.
- 이전 트래픽 진단에서 제목·색인·내부 링크 관찰 동결이 진행 중이라면, 이를 확인하고 해당 변경의 배포 창을 분리함. 원고 준비와 인증 동선 검토까지 막을 필요는 없음.
- 기존 [트래픽 회복 계획](<C:/Users/kim donghyun/Documents/popspot2/docs/superpowers/plans/2026-09-02-traffic-recovery-to-300.md>)의 과거 수치를 현재 기준선으로 자동 재사용하지 않음. 이 통합 계획은 그 문서의 원인 진단 결과를 새로 확정하지 않음.

### 9.1 작업별 보안 게이트

**보안 작업이 남아 있다고 이 계획 전체를 멈추지 않음.** 콘텐츠 원고, 비회원 비교 UI 설계, 기존 계측 정의 정리, 검색·필터 편의 개선, 출처·갱신일 표시는 별도 차단 없이 진행함. 아래 작업만 해당 게이트에 묶음.

| 작업 | 보안 게이트 |
|---|---|
| 상세·랜딩 콘텐츠 | 별도 차단 없음. 출처·저작권·개인정보 정책 적용 |
| 비회원 비교·발견 | 기존 공개 데이터만 쓰면 진행 가능 |
| 회원 관심 정보 | API 인증 + **자원 소유권 검사** 필요 |
| 지속 로그인 | OAuth 앱 전환과 구방식 발급 종료 필요(§5.3 관문) |
| 앱 출시 | OAuth 전환 · 의존성 감사 · 앱 CI 필요 |
| 종료 알림 | 동의·취소·중복 방지 + 운영 시크릿 검증 필요(§7.6) |
| Google API 연동 | 키 교체·제한 + **실행 중 서비스가 새 키를 쓰는지 확인** 필요 |

**Git 코드만으로 증명되지 않는 것이 있음.** "Google API 키 두 개가 아직 유효함", "서버·웹 변경이 실제 운영에 배포됨" 은 제공자 콘솔과 운영 환경에서 별도의 완료 증거를 남겨야 함.

### 9.2 새 API 의 완료 조건

2026-09-05 부터 CI 에 `ControllerAuthorizationInventoryTest` 가 있음. 매핑이 있는 모든 `@RestController` 는 **클래스 `@PreAuthorize` / `FULLY_PUBLIC` / `MIXED`** 중 정확히 하나로 분류돼야 하며, 어디에도 없으면 CI 가 막음. 기존 컨트롤러의 공개·비공개 구성이 바뀔 때도 분류를 갱신해야 함.

**다만 이 검사는 "공개 여부를 고민했는가" 만 확인함.** 다른 사람의 관심 목록이나 알림 설정을 조회할 수 없는지까지는 보장하지 않음(검사 주석에도 소유권 검사는 범위 밖이라고 적혀 있음). 새 API 의 완료 조건은 넷임.

- [ ] 컨트롤러 공개·비공개 분류
- [ ] 인증 없는 요청의 기대 결과
- [ ] 다른 회원 자원 접근 차단
- [ ] 관리자와 일반 회원 권한 분리

비교·발견이 반드시 새 컨트롤러를 필요로 하는 것은 아니지만, **새 컨트롤러나 새 매핑이 생기는 순간** 이 관문을 적용함.

### 10.1 앱 코드의 실제 위치

`origin/main` 에도 `popspot-app` 은 있으나 **오래된 최소 앱**임. 소셜 로그인(`socialAuth.ts`)도, 검사 파일도, `typecheck`·`test` 스크립트도 없음. 실측:

| | `origin/main` | `feat/app-design-17screens` |
|---|---|---|
| 앱 소스 파일 | 11개 | 142개 |
| `socialAuth.ts` | 없음 | 있음 (**아직 `{code}` 만 보내는 구방식**) |
| 검사 파일 | 0개 | 있음 |

**기능 브랜치를 통째로 병합하는 것을 선행조건으로 삼지 않음.** 그 브랜치에는 2026-09-05 에 `main` 으로 들어간 OAuth·권한 검사 변경이 없어, 통째 병합하면 그것들이 되돌아갈 수 있음.

이관 절차는 다음임.

- [ ] 1. 기능 브랜치의 **기준 커밋 SHA 를 고정**함
- [ ] 2. 최신 `origin/main` 에서 깨끗한 통합 브랜치를 만들고, 그 커밋의 `popspot-app` **트리 전체를 Git 기준으로 이관**함. 추가·변경·삭제 파일 목록을 대조함
- [ ] 3. **탐색기나 현재 작업 폴더에서 수동 복사하지 않음** — 삭제된 옛 파일·이름 변경·바이너리 폰트·실행 설정을 놓치고, 미커밋 변경이 섞이며, 어느 시점의 앱을 옮겼는지 재현할 수 없음
- [ ] 4. 앱 OAuth 에 challenge·verifier 와 App Links 를 적용함. **트리를 그대로 옮겨 출시하면 이번에 막은 취약 클라이언트를 다시 만드는 셈임**
- [ ] 5. 구방식 자동 후퇴를 금지함
- [ ] 6. `typecheck`·`test` 스크립트와 앱 CI 를 추가함
- [ ] 7. Android 실기기에서 로그인과 복귀를 검증함
- [ ] 8. 그 결과만 배포 대상으로 씀

각 개별 개발계획은 현재 파일과 인터페이스, 실패를 재현하는 테스트, 변경 코드, 검증 명령, 호환성, 배포·중단 절차를 포함해야 함. 기존 대형 파일 전체를 무관하게 리팩터링하지 않음. 코드 작성 시 각 프로젝트의 AGENTS.md와 해당 프레임워크 버전 문서를 먼저 확인함.
