# 백엔드를 Oracle Cloud 로 옮긴다

2026-08-14 결정 · 2026-08-19 개정. 집 Proxmox VM 을 상시 운영에서 내리고 Oracle Cloud 서울 리전으로 옮긴다.

## 왜 옮기나

집 VM 이 2026-08-13 부터 접속 불가다. 그런데 이번이 처음이 아니다.

| 날짜 | 증상 | 조치 |
|---|---|---|
| 08-11 | Funnel 전체 장애 | `systemctl restart tailscaled` |
| 08-12 아침 | 실패율 53%, 30분 연속 502 | 재시작 |
| 08-13 | VM 자체 접속 불가 | **미해결** |

복구되더라도 같은 일이 또 일어난다. 재시작 크론(`popspot-funnel-guard.sh`)은 완전 장애를 줄이는 장치지 원인을 없애지 못한다.

## 무엇이 걸려 있나 — 두 종류를 나눈다

이 구분이 계획 전체를 지배한다.

| | 복구 가능성 | 근거 |
|---|---|---|
| **공개 데이터**(팝업) | **재생 가능** | 크롤러가 만든 것이다. 2026-08-11 마커 스냅샷 949건도 있다 |
| **회원 데이터**(로그인·찜·채팅·결제) | **옛 DB 없이는 불가** | 사람이 만든 것이라 다시 만들 수 없다 |

옛 VM 이 영영 안 돌아와도 앞의 것은 지킬 수 있다. 둘을 한 덩어리로 묶으면 둘 다 잃는다.

## 1단계 — 서버 생성 · **여기에 분기가 있다**

목표: `VM.Standard.A1.Flex` · 2 OCPU · 8GB · Ubuntu 22.04 ARM64 · 부팅 50GB + 데이터 50GB

- 홈 리전 **South Korea Central (Seoul)**. 나중에 못 바꾼다. **Chuncheon 금지**
- `Always Free Eligible` 표시 확인
- 예산 알림 1달러 — 알림이지 결제 차단이 아니다
- **Compartment Quota** — A1 OCPU·메모리·볼륨을 무료 허용량 이하로 제한하고, 쓰지 않을 자원
  종류는 0 으로 막는다. "모든 비용을 완벽히 차단" 하는 장치는 아니고 실수로 유료 자원을 만드는 것을 막는다

**ARM 무료는 서울에서 자리가 잘 안 난다.** 시간 상한을 둔다.

| | |
|---|---|
| 48시간 안에 확보 | 그대로 진행 |
| 48시간 넘김 | 아래에서 선택 — **자동으로 유료를 고르지 않는다** |

| 대안 | 사양 | 판단 |
|---|---|---|
| x86 Micro ×2 (Always Free) | 1/8 OCPU · 1GB | Spring Boot + PG + Redis 를 한 대에 못 올린다 |
| 유료 소형 | 월 1~2만원대 | **무료 원칙을 깨는 결정 — 사용자 승인 필요** |
| 다른 무료 제공자 | — | 조사 필요 |

### Oracle 무료 서버를 어떻게 정의할 것인가

**"절대 장애 없는 본거지" 가 아니라 "비용 우선 운영 서버" 다.**

- Always Free 인스턴스는 **7일간 CPU·네트워크·메모리가 모두 낮으면 회수**될 수 있다
- 회수된 뒤 같은 사양을 즉시 다시 만든다는 보장이 없다
- 서울 리전 용량 부족이 반복될 수 있다

그래서 12단계(백업)가 선택이 아니라 전제다.

## 3단계 — Flyway 두 경로 사전 연습

**운영에 붙이기 전에 별도 PostgreSQL 에서 둘 다 성공시킨다.**

| DB 상태 | 절차 | 어느 분기에서 쓰나 |
|---|---|---|
| 빈 DB | `V1` → `V33` 전체 | **8-B** 임시 공개 DB |
| 스키마는 있는데 이력 없음 | 실제로 V28 수준인지 **대조한 뒤에만** baseline 28 → `V29~V33` | 예외(이력 유실) |
| `flyway_schema_history` 있음 | 기록된 최신 성공 버전부터 이어서. **임의 baseline 금지** | **8-A** 옛 DB 복원본 |

운영이 Flyway 로 돌아왔으므로 복원본은 세 번째다. **"V28 수준인지" 는 눈대중으로 정하지 않는다** —
V28 까지의 마이그레이션이 만드는 테이블·컬럼 목록과 실제 스키마를 대조하는 절차를 먼저 만든다.
기준을 낮게 잡으면 비멱등 마이그레이션이 재실행되고, 높게 잡으면 필요한 것이 건너뛰어진다.

### 문서가 코드와 어긋나 있다 — 같이 고친다

| 위치 | 적힌 값 | 실제 |
|---|---|---|
| `application-prod.properties:26` | `baseline-version=28` | **이게 맞다** |
| `deploy/DEPLOY_CHECKLIST.md:101` | `baseline-version=22`, V23 부터 | 낡음 |
| `deploy/README_DEPLOY.md:137` | 동일 | 낡음 |
| `deploy/DEPLOY_CHECKLIST.md:76` | V30 적용 확인 | 같은 문서 안에서도 어긋남 |

이 문서를 그대로 따르면 **잘못된 SQL 이 재실행되거나 기동이 중단된다.** 배포 문서를 `28` 기준으로 고친 뒤 진행한다.

## 4단계 — OS 보안 · 방화벽 · Tunnel

- root 직접 로그인 · 비밀번호 SSH 차단, 키 로그인만
- SSH 접속 IP 제한 · UFW 기본 차단
- PostgreSQL · Redis 는 `127.0.0.1` 만 바인딩. 5432 · 6379 외부 개방 금지
- **80 · 443 을 인터넷에 직접 열지 않는다** — Cloudflare Tunnel 로만
- `.env` 권한을 운영 계정만
- 자동 보안 업데이트
- **새로 발급하는 것**(인프라 자격증명): PostgreSQL 비밀번호 · Redis 비밀번호 · JWT 비밀키 ·
  Cloudflare Tunnel 토큰 · 서버 SSH 키
- **그대로 복원하는 것**: 회원·관리자 **비밀번호 해시**. 관리자 비밀번호를 바꿔야 하면 복원 후
  정상적인 재설정 절차로 바꾼다 — 해시를 손대지 않는다
- JWT 키를 바꾸면 기존 로그인 세션이 전부 풀린다. 이번 이전에서는 의도한 결과로 본다

### 방식을 하나로 확정한다

기존 배포 문서의 **`A 레코드 + 80/443 개방 + Certbot`** 방식과 **Tunnel** 을 섞지 않는다. Tunnel 로 확정하고 문서도 그 방식으로 고친다.

## 5단계 — 데이터 디스크 배치

PostgreSQL 데이터 디렉터리와 업로드 경로를 **부팅 디스크가 아니라 데이터 디스크에** 둔다. 부팅 디스크를 갈아도 데이터가 남는다.

### 마운트에 실패하면 서비스도 뜨면 안 된다

연결이 안 됐는데 PostgreSQL 이 그냥 기동되면 **빈 경로를 새 데이터 디렉터리로 초기화**한다. 나중에
마운트를 고치는 순간 그 사이에 쌓인 것이 사라지고, 더 나쁘게는 원래 데이터가 가려진다.

- `UUID` 로 마운트한다 (장치명은 부팅마다 바뀔 수 있다)
- PostgreSQL·백엔드 systemd 유닛에 `RequiresMountsFor` 를 건다
- **마운트 실패 시 기동을 차단한다.** 조용히 빈 디렉터리로 시작하는 것보다 안 뜨는 편이 낫다

## 6단계 — 백업 자동화 · **데이터 투입 전에**

**이 사고의 원인은 VM 이 죽은 것이 아니라 백업이 그 VM 안에만 있었던 것이다.** 그래서 순서가 이렇다.

```
서버 설치 → 백업 자동화 → 실제 복원 시험 → 데이터 투입 → 서비스 연결
```

한 번이라도 쓰기를 열기 전에 PostgreSQL 과 업로드 파일의 **외부** 백업이 실제로 동작해야 한다.

- PostgreSQL 매일 덤프 · 업로드 파일 매일 증분
- Oracle Object Storage 최근 7일
- **개인 PC 또는 NAS 주간 백업** — 오라클 계정 자체에 문제가 생겨도 복구 가능해야 한다
- 덤프는 암호화
- **월 1회 실제 복원 테스트**

## 7단계 — 헬스체크 (도메인 연결 전)

빈 DB 로 `/actuator/health` 와 공개 API 를 확인한다. **아직 `api.popspot.co.kr` 를 연결하지 않는다.**

## 8단계 — 옛 VM 복구 여부에 따라 분기

### 8-A. 복구됨

**깨끗한 새 DB 에 옛 DB 전체를 복원한다. 임시 공개 DB 는 폐기한다.**

임시 DB 와 옛 DB 를 **합치지 않는다.** 합치면 다음이 충돌한다.

- 팝업 ID 와 시퀀스(자동 번호)
- 찜·스탬프·동행 글이 참조하는 팝업 FK
- 결제 고유번호
- 크롤 이력 · 관리자 계정
- **Flyway 적용 기록**
- 업로드 파일 경로

즉 임시 DB 는 **처음부터 버릴 수 있는 것**으로 만든다.

확보할 것: PostgreSQL 전체 덤프 · DB 사용자와 권한 · 업로드 이미지 · `.env` · OAuth 설정 · Tunnel 설정 · JAR 버전 · Flyway 버전. 덤프 직전에 옛 백엔드를 멈춰 도중에 데이터가 바뀌지 않게 한다. Redis 는 캐시라 새로 시작한다.

### 8-B. 복구 안 됨

임시 공개 DB(스냅샷 949건을 **원래 ID 로** 시드) 또는 프론트 스냅샷만으로 운영한다.

ID 를 보존해야 하는 이유: `/popup/3617` 같은 URL 이 이미 검색엔진에 등록돼 있다. 새로 크롤해 새 ID 를 받으면 그 URL 이 전부 죽는다.

**옛 DB 가 영구 복구 불가로 확정됐을 때만** 임시 DB 를 정식 공개 DB 로 승격한다.

## 9단계 — 쓰기 차단은 서버에서 한다

화면에서 버튼만 숨기는 것으로 끝내지 않는다. **서버 또는 Cloudflare 에서 공개 `GET` 만 통과시키고** 로그인·결제·업로드·채팅 요청을 실제로 막는다.

### 자동 작업 전면 정지

옛 DB 를 확보하기 전에는 **DB 를 바꾸는 것을 전부 끈다.**

- 팝업 크롤러
- 사진 자동 채우기
- 중복 정리
- 번역 자동 채우기
- 만료 상태 변경
- 찜 알림
- 관리자 로그 정리

"읽기 전용으로 운영하면서 크롤러로 채운다" 는 모순이다. 크롤러는 쓰기다.

**다만 만료는 다르다.** 만료 상태를 DB 에 기록하는 작업은 멈추되, **공개 API 는 조회할 때마다**
오늘 날짜 기준으로 마감된 팝업을 걸러야 한다. 안 그러면 서버가 오래 돌수록 끝난 팝업이 목록에 쌓인다.
끄는 것은 "쓰기" 지 "거르기" 가 아니다.

### 노출 정책

| 종류 | 상세 조회 | 색인 |
|---|---|---|
| 진행 중 · 날짜·장소 정상 | ○ | ○ |
| 중복(08-12 에 숨긴 61건) | ○ | **noindex** |
| 마감 | ○ (종료 안내) | **noindex** |
| 날짜 비정상 | ○ | **noindex** |

**949개 ID 를 조회 가능하게 유지하는 것과 검색에 노출하는 것은 다르다.** 대표 ID 를 모르는 중복은 임의로 연결하지 않는다.

건수는 계산으로 확정한다. `949 − 61 − 24` 같은 단순 뺄셈을 쓰지 않는다 — 중복과 만료가 겹칠 수 있고 날짜는 그날 기준으로 다시 재야 한다.

## 11단계 — 도메인 전환 (승인 후)

**서버가 준비되고 검증을 통과한 뒤에** 연결한다. 순서를 지킨다.

1. Cloudflare Tunnel 생성
2. `api.popspot.co.kr` 를 Tunnel 에 연결
3. 헬스체크 확인
4. **OAuth 제공자에 새 콜백 주소 추가** (기존 것은 아직 두고)
5. Vercel `NEXT_PUBLIC_API_URL` 변경 후 재배포
6. 로그인·업로드·WebSocket 확인
7. 기존 콜백 주소 제거

지금 백엔드 주소는 `vm-113.tailc57dd4.ts.net` 이고 이 값이 세 곳에 파생된다 — Vercel 환경변수, `next.config.ts` rewrite, CSP 의 `connect-src`·`img-src`(`backendUrl.origin`). 고정 도메인을 한 번 잡아 두면 **다음 이전부터는 DNS 만 바꾸면 된다.**

**서버보다 먼저 Vercel 환경변수를 바꾸면 안 된다.** 지금 `api.popspot.co.kr` 는 404 다.

## 13단계 — 크롤러 재개 (단계적으로)

바로 정기 실행에 넣지 않는다.

```
수동 1회 실행
  → 생성·수정·중복·토큰 사용량 보고
  → 결과 검수
  → 문제 없으면 04시·16시 정기 실행 허용
```

**임시 공개 DB 라면 영구 승격이 확정되기 전까지 크롤러를 아예 실행하지 않는다.**

## 14단계 — 48시간 관찰

5xx 비율 · 로그인 실패율 · DB 연결 수 · CPU/메모리/디스크 · JVM 힙 · Redis 메모리 · 업로드 성공률 · WebSocket · 크롤 수집량 · Cloudflare 오류 · 검색엔진 수집 오류 · **무료 한도**.

## 15단계 — 옛 VM 종료 (1~2주 뒤)

48시간은 **새 서버 관찰 기간**이지 옛 VM 폐기 시점이 아니다.

```
48시간 정상 확인
  → 옛 VM 의 네트워크·백엔드·크롤러 차단
  → 1~2주 보관
  → 외부 백업에서 실제 복원되는지 확인
  → 개인정보가 남은 디스크를 안전 삭제
```

## 폐기한 안

- **임시 DB 와 옛 DB 병합** — ID·시퀀스·FK·Flyway 이력이 충돌한다. 깨끗한 DB 에 전체 복원하고 임시는 버린다
- **공개 운영 중 크롤러 가동** — 읽기 전용과 모순이다
- **백업을 관찰 이후로 미루기** — 이번 사고의 원인이 그것이다
- **서버보다 먼저 Vercel 주소 변경** — 지금 그 도메인은 404 다
- **비상 모드 재구현** — 이미 배포돼 동작 중이다
