# 백엔드를 Oracle Cloud 로 옮긴다

2026-08-14 결정. 집 Proxmox VM 을 상시 운영에서 내리고 Oracle Cloud 서울 리전을 본거지로 삼는다.

## 왜 옮기나

집 VM 이 2026-08-13 부터 접속 불가다. 그런데 이번이 처음이 아니다.

| 날짜 | 증상 | 조치 |
|---|---|---|
| 08-11 | Funnel 전체 장애 | `systemctl restart tailscaled` |
| 08-12 아침 | 실패율 53%, 30분 연속 502 | 재시작 |
| 08-13 | VM 자체 접속 불가 | **미해결** |

복구되더라도 같은 일이 또 일어난다. 재시작 크론(`popspot-funnel-guard.sh`)은 완전 장애를 줄이는 장치지 원인을 없애지 못한다.

## 무엇이 걸려 있나 — 두 종류를 나눈다

이 구분이 계획 전체를 지배한다.

| | 복구 가능성 | 근거 |
|---|---|---|
| **공개 데이터**(팝업) | **재생 가능** | 크롤러가 만든 것이다. 게다가 2026-08-11 마커 스냅샷 949건이 있다 |
| **회원 데이터**(로그인·찜·채팅·결제) | **옛 DB 없이는 불가** | 사람이 만든 것이라 다시 만들 수 없다 |

그래서 **공개 사이트는 옛 VM 을 기다리지 않고 살린다. 쓰기 기능은 옛 DB 를 확보할 때까지 닫는다.**

옛 VM 이 영영 안 돌아올 경우, 앞의 것은 정상 운영되고 뒤의 것만 잃는다. 둘을 한 덩어리로 묶으면 둘 다 잃는다.

## 지금 상태(2026-08-14)

```
popspot.co.kr        200 (프론트는 Vercel 이라 살아 있음)
/api/*               502 DNS_HOSTNAME_NOT_FOUND
sitemap.xml          15건  (정상 930건)
feed.xml             1건   (정상 173건)
```

사이트맵·RSS 가 무너진 것이 가장 급하다. 08-11 에 색인 396건을 열고 08-12 에 RSS 를 173건으로 늘렸는데, 그 작업이 지금 통째로 무효다.

## 0단계 — 도메인 먼저 (서버보다 먼저)

**`api.popspot.co.kr` 를 만든다.**

지금 백엔드 주소는 `vm-113.tailc57dd4.ts.net` 이고, 이 값이 세 곳에 박혀 있다.

- Vercel `NEXT_PUBLIC_API_URL`
- `next.config.ts` 의 rewrite destination
- CSP 의 `connect-src` · `img-src` (`backendUrl.origin` 으로 파생)

서버를 옮길 때마다 이 셋을 고치고 프론트를 재배포해야 한다. 고정 도메인을 앞에 두면 **다음부터는 DNS 만 바꾸면 된다.** OAuth 리디렉트 URI 도 여기에 묶으면 서버 이전과 무관해진다.

이건 오라클 자리가 안 나도 지금 할 수 있고, 이후 모든 단계를 싸게 만든다.

## 1단계 — 비상 읽기 전용 모드 (오라클과 병렬)

오라클은 빨라도 며칠이다. 그동안 사이트맵 15건 상태를 두면 08-11 에 연 396건이 크롤 큐에서 밀린다.

별도 문서로 상세 설계가 있다(§비상 모드). 요지만 적는다.

1. 08-11 마커 949건을 저장소로 옮기고 해시·출처·생성시각 기록
2. 공통 스냅샷 로더 작성 — 백엔드 성공 시 그쪽, 실패 시 스냅샷
3. **빌드가 백엔드 없이 통과하는지 먼저 확인** — `popups/[slug]/page.tsx` 가 fetch 3회 실패 시 빌드를 중단한다. 여기가 막히면 배포 자체가 안 된다
4. 사이트맵·RSS 를 로더에 연결 (가장 급함)
5. 목록·지도·SEO 랜딩·최소정보 상세
6. 쓰기 기능 중단 + "마지막 확인: 2026-08-11" 표시
7. 실시간·영업중·혼잡도는 표시하지 않는다

## 2단계 — 오라클 계정과 리전

- 홈 리전을 **South Korea Central (Seoul)** 로. 나중에 못 바꾼다
- **Chuncheon 선택 금지**
- `Always Free Eligible` 표시 확인
- 예산 알림 1달러 — 다만 이건 알림이지 결제 차단이 아니다

## 3단계 — 서버 생성 · **여기에 분기가 있다**

목표: `VM.Standard.A1.Flex` · 2 OCPU · 8GB · Ubuntu 22.04 ARM64 · 부팅 50GB + 데이터 50GB

**ARM 무료 인스턴스는 서울에서 자리가 잘 안 난다.** `Out of host capacity` 가 며칠씩 이어지는 일이 흔하다. 그래서 시간 상한을 둔다.

```
48시간 안에 A1.Flex 확보  →  그대로 진행
48시간 넘김               →  아래 중 선택
```

| 대안 | 사양 | 판단 |
|---|---|---|
| x86 Micro ×2 (Always Free) | 1/8 OCPU · 1GB | Spring Boot + PG + Redis 를 한 대에 못 올린다. DB 를 분리해도 빠듯 |
| 유료 소형 인스턴스 | 월 1~2만원대 | 안정성은 확실. **무료 원칙을 깨는 결정이라 사용자 승인 필요** |
| 다른 무료 제공자 | — | 조사 필요 |

**유료 서버를 자동으로 고르지 않는다.** 상한에 걸리면 멈추고 보고한다.

## 4단계 — 보안 기본

- root 직접 로그인 · 비밀번호 SSH 차단, 키 로그인만
- SSH 접속 IP 제한
- UFW 기본 차단
- PostgreSQL · Redis 는 `127.0.0.1` 만 바인딩. 5432 · 6379 외부 개방 금지
- 80 · 443 을 인터넷에 직접 열지 않는다 — Cloudflare Tunnel 로만
- `.env` 권한을 운영 계정만 읽게
- 자동 보안 업데이트
- **DB · JWT · 관리자 비밀번호는 새로 발급** (옛 값을 옮기지 않는다)

## 5단계 — ARM64 검증

Java 21 이라 대체로 돌지만 확인할 것이 있다.

- 백엔드 전체 테스트 · JAR 실행
- PostgreSQL · Redis 연결
- 이미지 업로드 · 판별
- 이메일 발송 · OAuth · WebSocket 채팅
- 크롤러
- `cloudflared` ARM64 실행
- 배포 스크립트의 경로 호환성

ARM 에서 못 쓰는 라이브러리가 나오면 그 부분만 교체한다. 프론트는 Vercel 이라 영향 없다.

## 6단계 — 빈 서버 기동

OpenJDK 21 · PostgreSQL · Redis · systemd · Cloudflare Tunnel · 백엔드 배포까지. 빈 DB 로 `/actuator/health` 와 공개 API 를 확인한다.

**아직 도메인을 연결하지 않는다.**

## 7단계 — 공개 데이터 시드 (**옛 VM 과 무관**)

여기가 이 계획의 핵심이다.

08-11 스냅샷 949건을 **원래 ID 그대로** 새 DB 에 넣는다. `id · name · nameEn · nameJa · location · locationEn · locationJa · latitude · longitude · category · startDate · endDate`.

ID 를 보존해야 하는 이유: `/popup/3617` 같은 URL 이 이미 검색엔진에 등록돼 있다. 새로 크롤해 새 ID 를 받으면 그 URL 이 전부 죽는다.

시드 뒤:

- 공개 API 만 도메인 연결 (읽기 전용)
- 크롤러를 돌려 소개 · 사진 · 링크를 채운다 — 스냅샷에는 없는 값이다
- **회원 기능은 계속 닫아둔다**

이 시점에 공개 사이트와 SEO 가 정상으로 돌아온다.

### 노출 정책

| 종류 | 상세 조회 | 색인 |
|---|---|---|
| 진행 중 · 날짜·장소 정상 | ○ | ○ |
| 중복(08-12 에 숨긴 61건) | ○ | **noindex** |
| 마감 | ○ (종료 안내) | **noindex** |
| 날짜 비정상 | ○ | **noindex** |

**949개 ID 를 조회 가능하게 유지하는 것과 검색에 노출하는 것은 다르다.** 대표 ID 를 모르는 중복은 임의로 연결하지 않는다.

목록에 낼 건수는 계산으로 확정한다. `949 − 61 − 24 = 864` 같은 단순 뺄셈을 쓰지 않는다 — 중복과 만료가 겹칠 수 있고, 날짜는 오늘 기준으로 다시 재야 한다. 만료∩중복 교집합도 따로 기록한다.

## 8단계 — 옛 VM 데이터 확보 (**복구되면**)

확보할 것: PostgreSQL 전체 덤프 · DB 사용자와 권한 · 업로드된 프로필/채팅 이미지 · `.env` · OAuth 설정 · Tunnel 설정 · 배포 중인 JAR 버전 · Flyway 버전.

백업 직전에 옛 백엔드를 멈춰 덤프 도중 데이터가 바뀌지 않게 한다.

Redis 는 캐시라 새로 시작한다. 영구 보존이 필요한 값이 있는지만 따로 확인한다.

## 9단계 — 회원 데이터 병합

7단계에서 공개 데이터가 이미 들어가 있으므로 **덮어쓰기가 아니라 병합**이다. 순서와 충돌 처리를 설계해야 한다.

- 회원 · 찜 · 스탬프 · 동행 · 채팅 · 결제 복원
- 팝업 테이블은 옛 덤프와 시드본 중 **어느 쪽을 진실로 볼지 정한다** (옛 덤프가 더 완전하다면 그쪽)
- Flyway 버전과 실제 스키마 대조
- 업로드 파일 복사 후 소유자 · 권한 교정

건수 비교: 회원 · 팝업 · 찜 · 동행 · 결제 · 파일 · 크롤 이력 · 관리자 계정 · 마이그레이션 버전.

**숫자가 맞지 않으면 쓰기 기능을 열지 않는다.**

## 10단계 — 쓰기 기능 개방 전 검증

공개 API · 지도 · SEO 랜딩 · 상세 · 사이트맵 · RSS · Google/Kakao 로그인 · JWT 만료 · 찜 추가삭제 · 프로필 업로드 · 채팅 업로드 · WebSocket · 관리자 로그인 · 결제 검증 · 크롤러 수동 실행 · 마감 제외 · CORS · 보안 헤더 · 응답 속도.

결과를 보고하고 **승인받은 뒤** 개방한다.

## 11단계 — 관찰 48시간

5xx 비율 · 로그인 실패율 · DB 연결 수 · CPU/메모리/디스크 · JVM 힙 · Redis 메모리 · 업로드 성공률 · WebSocket · 크롤 수집량 · Cloudflare 오류 · 검색엔진 수집 오류 · 무료 한도.

## 12단계 — 백업 (이번 사고의 진짜 교훈)

**이 사고의 원인은 VM 이 죽은 것이 아니라 백업이 그 VM 안에만 있었던 것이다.** 같은 구조를 다시 만들면 안 된다.

- PostgreSQL 매일 덤프 · 업로드 파일 매일 증분
- Oracle Object Storage 최근 7일
- **개인 PC 또는 NAS 주간 백업** — 오라클 계정 자체에 문제가 생겨도 복구 가능해야 한다
- 덤프는 암호화
- **월 1회 실제 복원 테스트** — 이걸 안 하면 백업이 있는지 없는지 모른다

## 13단계 — 옛 VM 처리

1~2주 안정 뒤 결정한다. 즉시 삭제하지 않는다. 네트워크만 차단하고 읽기 전용 비상 복구본으로 둔다.
