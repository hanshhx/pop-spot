# 보안·분석 플랜 (2026-08) — 진행 기록

A(즉시 보호) · B(관리자 보안) · C(방문 분석) · D(보안 관제) 네 묶음의 진행 상태와,
**왜 그렇게 했는지**를 남긴다.

이 문서를 쓰는 이유는 하나다. 판단 근거가 커밋 메시지와 대화에만 흩어져 있으면,
몇 달 뒤 "왜 이 값이 90일이지" · "왜 이 조합을 뺐지" 를 다시 조사하게 된다.
숫자는 그때의 실측이므로 지금 다시 재면 달라진다 — 날짜를 함께 적어 둔다.

## C — 방문 분석

### 완료

**C-1 수집 구조** (`V32__visit_event.sql`)
`visitor_id · session_id · event_type · popup_id · path · guest · created_at`.
행동 종류는 화이트리스트다 — 목록 밖의 값은 조용히 버린다. 자유 문자열로 두면
오타가 새 종류로 쌓여 집계가 갈라진다.

**C-2 보관기간·자동삭제** (`VisitService.deleteExpiredVisitLogs`)
매일 04:40 KST. `visit_log` 와 `visit_event` 를 **같은 기준**으로 지운다.
따로 두면 한쪽만 정리돼 방침의 90일 약속이 반만 지켜지는데, 그 어긋남은
아무 데도 드러나지 않는다.

**C-3 세션 · 신규/재방문** (`a1c080f`)
`GET /api/admin/visits/sessions?days=N`

- 수집은 이미 되고 있었고 **읽는 API 만 없었다.** 그래서 방문자 CSV 를 받아도
  재방문율을 계산할 수 없었다 — 유입만 늘리고 남는지는 모르는 상태였다.
- 신규를 따로 세지 않고 재방문을 센 뒤 뺀다. 두 쿼리의 기준이 달라지면 합이
  전체와 안 맞는다.
- `truncated` 를 함께 준다. 재방문 판정은 보관기간 안에서만 가능해서, 90일
  구간을 물으면 앞쪽이 전부 신규로 잡힌다. **이 값은 재방문율의 하한이다.**

**C-4 퍼널** (`e009626`)
`GET /api/admin/visits/funnel?days=N` — 방문 → 상세 열기 → 찜 → 예약·공식 링크
→ 다시 방문. 각 칸은 **사람 수**(횟수가 아니다).

- 뒤쪽 두 단계는 **수집 자체가 없었다.** `wishlist_add` · `outbound_click` 을
  새로 만들었다. 없는 것으로 퍼널을 그리면 허구가 된다.
- 첫 칸만 `visit_log` 에서 온다 — 페이지만 열고 아무것도 안 누른 사람이 분모에
  들어가야 "몇 명이 그냥 갔나" 가 보인다.
- 재방문 칸은 **세션이 달라야** 센다. 같은 세션 안의 행동을 세면 한 번 왔다 간
  사람이 전부 재방문이 된다.
- 수집 시작일은 `MIN(created_at)` 으로 데이터에 묻는다. 설정에 적으면 배포마다
  사람이 손대야 하고, 잊으면 또 틀린다.
- 뒤 칸이 앞 칸보다 커도 100% 로 자르지 않는다 — 억지로 맞추면 "이상하다" 는
  신호까지 지워진다.

### D-4 는 계층이 아니라 열거로 (2026-08-06)

역할 셋. `ROLE_ADMIN`(전권) · `ROLE_SECURITY` · `ROLE_ANALYTICS`.
`User.role` 은 칼럼이 하나라 **한 사람에 하나**다.

**지금은 동작이 달라지지 않는다.** 관리자가 `ROLE_ADMIN` 하나뿐이고 그건 모든 것을
받는다. 두 번째 사람에게 **방문 통계만** 열어 줄 수 있도록 자리를 만든 것이다.

`ROLE_ADMIN > ROLE_SECURITY` 같은 **계층(RoleHierarchy)을 쓰지 않았다.** 짧지만 그
계층이 메서드 보안까지 연결되는지가 Spring 버전마다 다르고, 연결이 안 되면 증상이
**"관리자가 자기 화면에서 403"** 이다. 되돌리려면 배포를 다시 해야 하는데 그 배포도
관리자 화면 없이 해야 한다. 장황해도 `hasAnyRole('ADMIN','SECURITY')` 처럼 그대로 적는다.

**관문이 둘**이라는 것을 잊지 말 것 — `SecurityConfig` 의 URL 규칙이 먼저 걸러내고
컨트롤러의 `@PreAuthorize` 가 한 번 더 본다. 한쪽만 고치면 안 된다.

URL 규칙은 **나눈 경로만 앞에 적고** 나머지는 기존 `/api/admin/**` → `ADMIN` 에
떨어지게 뒀다. 새로 생기는 관리자 화면이 **기본적으로 닫혀 있는** 쪽이라 안전하다.

`AdminRoleSeparationTest` 가 넷을 고정한다 — 모든 화면이 여전히 ADMIN 을 받는지(양쪽
관문 다), 쪼갠 것이 실제로 반영됐는지, 분석 담당이 보안 화면에 못 들어가는지.

**두 번째 사람을 받을 때**: `USERS.role` 에 `ROLE_ANALYTICS` 를 넣으면 방문 통계와
서버 지표만 보인다. D-3 의 재확인 문턱은 보안 화면에만 걸리므로 그 사람에게는
2단계 인증을 물을 일이 없다.

### D-3 은 역할이 아니라 문턱으로 갈랐다 (2026-08-06)

관리자가 한 명이라 `ROLE_SECURITY` / `ROLE_ANALYTICS` 를 만들어 봐야 **같은 사람이
둘 다 갖는다** — 오늘 바뀌는 것이 없다. 그건 두 번째 관리자가 생길 때(D-4) 할 일이다.

대신 **같은 계정이라도 무엇을 보느냐에 따라 요구하는 증명을 다르게** 했다. 가르는
기준은 "탈취된 세션이 그것으로 무엇을 할 수 있는가" 다.

| | 문턱 | 이유 |
|---|---|---|
| 감사 로그 · 보안 현황판 | ADMIN + **본인 재확인** | 관리자가 어디서 접속하는지가 적혀 있다 |
| IP 임시 차단 | ADMIN + **본인 재확인** | 진짜 관리자를 잠그거나 자기를 풀 수 있다 |
| 방문 통계 · 서버 지표 | ADMIN | 훔쳐봐도 할 수 있는 일이 없다. 자주 보는 화면이다 |
| **전체 로그아웃** | ADMIN | **비상 스위치 앞에 문을 두지 않는다** |

이 둘이 **이어져 하나의 공격**이 된다는 것이 감사 로그를 읽기까지 막은 이유다 —
로그에서 관리자 IP 를 읽어 그 IP 를 차단하면 진짜 관리자를 밀어낼 수 있다.
`AdminReauthScopeTest` 가 이 목록이 넓지도 좁지도 않은지 고정한다.

### ⚠ D-3 은 환경변수를 켜야 작동한다

`app.admin.reauth.enabled` 기본값이 **false** 이고, 꺼져 있으면 `isSatisfied` 가
전부 통과시킨다. 즉 배포만 해서는 **아무것도 바뀌지 않는다.**

```bash
APP_ADMIN_REAUTH_ENABLED=true
```

이건 이 저장소의 기존 방식이다(2단계 인증도 같다) — 코드를 먼저 올려 아무것도
안 바뀌는 것을 확인한 뒤 켠다. 되돌릴 때도 값만 지우면 된다.

켤 때 확인할 것: 관리자 계정에 **2단계 인증이 등록돼 있어야** 한다. 없으면
`Method.NONE` 이라 막지 않고 로그만 크게 남긴다(잠기지는 않는다).

### IP 신뢰 경로 검증 결과 (2026-08-06)

경로가 두 갈래다.

| | 가는 길 | 백엔드가 보는 IP |
|---|---|---|
| A | 브라우저 → Vercel → Funnel → 서버 | 진짜 접속자 IP (서명 검증됨) |
| B | 브라우저 → **Funnel 직결** | 서명 없음 → Funnel 내부 주소 **하나** |

`proxy.ts` 는 서명을 붙이는 유일한 곳인데 **Vercel 을 지나는 요청에만** 실행된다. B 는
Vercel 을 아예 안 지나므로 비밀키 설정 여부와 무관하게 **항상** 서명이 없다.

B 에 속하는 것: `/api/visits/events`, `/api/client-errors`, 아바타·채팅 업로드,
사진 백필, 중복 정리, 관리자 로그 스트림, OAuth 로그인 시작, 그리고 **`FormData` 인
모든 요청**(`api.ts` 의 `buildUrl`). 마지막 것은 경로 목록이 아니라 **조건**이라,
앞으로 추가되는 업로드는 전부 자동으로 여기 들어간다.

**D-2 를 만들 때 반드시 지킬 것 — 차단은 `trust == VERIFIED` 인 값에만 건다.**
강등된 값에 차단을 걸면 셋이 한꺼번에 터진다.

1. 백필·중복 정리·로그 스트림이 B 라서 **관리자가 자기 도구에서 잠긴다.**
2. 프로필 사진·채팅 이미지가 같은 주소를 써서 **전 사용자의 업로드가 동시에 죽는다.**
3. Funnel 주소를 직접 때리면 누구나 그 바구니를 고의로 넘길 수 있어, 자동 차단이
   **아무나 누를 수 있는 정지 버튼**이 된다.

`ClientIpResolver.resolve()` 가 `ClientIp(value, trust)` 를 돌려주도록 고쳤다(2026-08-06).
`Trust` 는 셋이다 — `VERIFIED`(차단 가능) · `DEGRADED`(서명 체계는 켜졌는데 증명 없음) ·
`UNCHECKED`(비밀키 미설정). **`DEGRADED` 와 `UNCHECKED` 를 뭉뚱그리면 안 된다** — 뭉치면
비밀키를 안 넣은 채 배포했을 때 감사 로그의 접속지가 전부 사라진다. `ClientIpResolverTest`
의 `uncheckedPreservesLegacyRecording` 이 그 실수를 잡는다(실증함).

### D-2 를 어떻게 지었나 (2026-08-06)

**사람이 걸고 시간이 푼다.** 자동으로 걸지 않는 것은 D-1 을 알림이 아니라 현황판으로
만든 것과 같은 이유다 — 임계값을 정할 "평소" 가 아직 없다. 게다가 자동 차단은 위
3번(공격자가 고의로 유발) 때문에 그 자체가 무기가 된다.

저장은 Redis. **자동 해제를 우리가 구현하지 않기 위해서다** — 만료를 직접 관리하면
청소가 밀렸을 때 임시 차단이 조용히 영구 차단이 된다. TTL 을 저장소에 맡기면 그
실패 방식이 아예 없어진다.

안전장치 넷, 전부 `IpBlockService` 안에 있다(부르는 쪽에 맡기면 다음 호출자가 빠뜨린다):

| 장치 | 막는 사고 |
|---|---|
| `VERIFIED` 아니면 차단 판정 자체를 안 한다 | 전 사용자 업로드 정지 · 관리자 자기 잠금 |
| 지금 접속 중인 주소는 못 건다 | 가장 흔한 자기 잠금 |
| 요청자 위치가 증명 안 되면 아무것도 못 건다 | 모르는 채로 되돌리기 어려운 일 하기 |
| 기간 상한 24시간 · 하한 1분 | "임시" 가 영구가 되는 것 (Redis TTL 0 = 만료 없음) |

**잠금 탈출구**: `/api/admin/security/ip-blocks/**` 는 차단 검사에서 제외된다. 관리자
IP 는 바뀌고 예전에 걸어 둔 주소를 다시 배정받을 수 있다. 그때 이 경로까지 막히면
서버에 직접 들어가야 한다. `IpBlockEscapeHatchTest` 가 이 제외가 **너무 좁지도 넓지도**
않은지 고정한다 — 좁으면 잠기고, 넓으면 차단이 통째로 무의미해지는데 **둘 다 평소엔
증상이 없다.**

## 이 플랜을 진행하며 만든 가드

정적 검사 테스트 넷. **전부 "틀린 것을 넣어 실패하는지" 까지 확인했다** — 통과하는
것만 보면 아무것도 안 보는 테스트를 통과했다고 믿게 된다. 실제로 두 번 그랬다.

| 테스트 | 막는 것 | 만든 계기 |
|---|---|---|
| `NativeQueryColumnsTest` | 네이티브 SQL 의 칼럼명 오타 | `p.id` 로 관리자 통계가 몇 주간 죽어 있었다 |
| `BeanConstructorTest` | 생성자 여럿 + `@Autowired` 없음 → 기동 실패 | 2026-08-05 실제 장애 |
| `VisitEventTypeContractTest` | 프론트/백엔드 행동 종류 불일치 | 한쪽만 고치면 화면은 정상, 통계만 0 |
| `indexableDetail.test.ts` | 색인 자격 판정의 양쪽 실패 | 느슨하면 얇은 페이지 191건, 빡빡하면 멀쩡한 게 빠진다 |

### 가드가 새어 나갔던 두 번

1. **주석 속 글자에 속음** — `src.contains("@Autowired")` 가 자바독의
   "`@Autowired` 를 지우지 마라" 에 걸려, 애너테이션을 떼도 통과했다.
   → 주석을 먼저 걷어낸다.
2. **파라미터 이름이 키워드로 읽힘** — `:from` 이 SQL 의 `FROM` 으로 파싱돼
   `e → and` 라는 엉뚱한 별칭이 만들어졌고, 그 쿼리가 검사에서 통째로 빠졌다.
   → 파라미터를 `:since`·`:until` 로, 패턴에 `(?<![:\w])` 추가.
